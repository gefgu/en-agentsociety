# Product Requirements Document: LLM Semantic Caching for Urban Simulator

## 1. Overview & Objective
The core objective of this feature is to drastically reduce the latency of the LLM-based urban simulator. Currently, agent inference takes between 4 and 30 seconds per simulation step. By implementing a semantic caching layer, the system will bypass live LLM inference for highly similar historical prompts, retrieving the previously selected `target_block`. The target latency for a cached query is in the millisecond range.

## 2. Core Logic & Architecture
Instead of sending every agent state to the LLM, the simulator will first check a vector database for a historical match. The system will rely on two primary confidence gates to ensure simulation integrity:

* **Vector Similarity:** The current prompt's embedding must closely match a historical prompt's embedding.
* **Token Probability (Logprobs):** The historical response must have been generated with a high degree of certainty by the LLM. 

If the LLM was mathematically certain about its output in the past, and the current context is nearly identical, the simulator will confidently reuse that output and force the same agent action. 



## 3. Tunable Simulation Parameters
To give researchers and users control over the speed-versus-variance tradeoff, the following parameters must be exposed globally before initializing a simulation run:

* **Similarity Threshold:** A configurable float (e.g., `0.99`) determining how close the new prompt's vector must be to the cached prompt's vector to trigger a hit.
* **Probability Threshold:** A configurable percentage (e.g., `0.80`, `0.90`) representing the minimum token log-probability the historical answer must possess to be eligible for retrieval.

## 4. Data & Infrastructure Requirements
* **Active Cache Database:** Qdrant will be utilized as the primary vector database during the live simulation to ensure millisecond retrieval times. (Note: ClickHouse remains for long-term historical data analytics).
* **Embedding Model:** FastEmbed (integrated via Qdrant) will be used to generate embeddings quickly without relying on heavy external API calls.
* **Input Formatting:** The system will embed the entire prompt string, preserving the exact order of the context features (e.g., `ctx_time`, `ctx_need`, `ctx_emotion`, etc.).
* **Payload Storage:** When an LLM inference *does* occur, the system must write the following to the Qdrant payload:
    * The complete text prompt.
    * The resulting `target_block`.
    * The token log-probabilities for the `target_block` decision.
    * The exact Model ID and Version (e.g., the Hugging Face model ID).
* **Excluded Data:** The `reason` field generated by the LLM is strictly for debugging and will not be retrieved or evaluated during the caching process.

## 5. Cache Invalidation & Isolation
* **Strict Model Matching:** Caches are strictly isolated by the LLM model version. A simulation running on `Model_A_v1` cannot retrieve cached actions generated by `Model_B_v2`. 
* **Version Control:** The exact Hugging Face ID (or equivalent model identifier) must be passed alongside the query to filter the Qdrant search results, ensuring the cache is inherently invalidated if the underlying model is swapped.

## 6. Success Metrics
* **Latency:** Reduction of agent step time from 4–30 seconds down to < 100 milliseconds for cached hits.
* **Cache Hit Rate:** Tracking the percentage of simulation steps successfully resolved via Qdrant versus falling back to live LLM inference.
