# Product Requirements Document (PRD): ClickHouse-Backed Checkpoint & Resume System

## 1. Overview
The goal of this feature is to implement a robust, continuous checkpoint and resume system for the `AgentSociety` urban simulator. Instead of relying on transient state or standard relational databases for agent memory, the system will migrate core simulation state storage to ClickHouse. By logging state changes at every simulation step, the framework will be able to reconstruct the exact state of the simulation following an interruption, crash, or pause.

## 2. Objectives
* **Seamless Resumption:** Automatically resume an interrupted simulation from the last valid step without manual intervention.
* **Complete State Reconstruction:** Rebuild agent memory, in-flight communications, and external environment states purely from event logs stored in ClickHouse.
* **Zero Performance Degradation:** Ensure state saving does not block the main simulation loop by utilizing asynchronous Ray actors.
* **Unified Data Layer:** Consolidate analytics, performance monitoring, and state persistence into a single ClickHouse backend.

---

## 3. Functional Requirements

### 3.1 Continuous State Capture
* **Frequency:** The system must capture and write state data at **every simulation step/tick**.
* **Agent Memory:** The payload must capture all three agent memory stores:
  * `KVMemory` (status and profile data)
  * `StreamMemory` (time-ordered event logs)
  * `SpatialMemory` (location history)
* **Message Bus:** All in-flight, unread messages currently residing in the `Messager` queue must be serialized and saved.
* **External Simulators:** The system must log sufficient environmental data (e.g., agent coordinates, financial transactions) to accurately recreate the physical and economic context within the external C++/Go mobility and economy simulators upon resume.

### 3.2 Automatic Resume Logic
* **Experiment Matching:** On simulation startup, the system will query ClickHouse for existing experiments matching both the **Experiment Name** and the **Experiment Configurations** (e.g., `Config` or `IndividualConfig` hashes/contents).
* **Completion Status Check:** If a matching experiment is found and its status is *not* `COMPLETED`, the engine will automatically enter "Resume Mode".
* **State Reconstruction Engine:** In Resume Mode, the system will replay or query the latest state payloads from ClickHouse to rehydrate the Ray actor instances (`AgentGroup`, `EnvironmentStarter`, `Messager`) before allowing the clock to tick forward.

### 3.3 Checkpoint Validation and Fallback
* **Integrity Checks:** Before resuming, the system must validate the integrity of the target step's data (e.g., checking for complete writes across all active agents).
* **Automatic Rollback:** If a checkpoint (step N) is deemed corrupted or incomplete due to a crash during a write, the system must automatically fall back to the previous valid step (N-1).

---

## 4. Non-Functional Requirements

### 4.1 Storage and Data Volume
* **Compression:** Rely heavily on ClickHouse's native columnar compression algorithms to manage the high volume of terabyte-scale data generated by per-step logging.
* **Retention:** Data will not be automatically pruned; all historical step data will be retained for deep post-simulation investigation and analytics.

### 4.2 Performance and Architecture
* **Asynchronous Writes:** Data ingestion must be handled by the ClickHouse actor (a dedicated Ray remote actor). The main simulation engine must fire-and-forget state payloads to this actor to ensure the main execution thread remains strictly non-blocking.

---

## 5. Database Schema & Query Strategy

### 5.1 Indexing
* **Primary Identifier:** The `experiment_id` (derived from the auto-generated UUID `id` in `Config`) will serve as the primary routing and indexing key across all state tables.
* **Sorting Keys:** Tables will be strictly ordered by `(experiment_id, step_number, agent_id)` to optimize for highly localized, sequential reads and writes.

### 5.2 Latest State Materialization
* **View-Based Rehydration:** Instead of performing complex table scans at startup, the system will rely on ClickHouse `VIEW`s (or `MATERIALIZED VIEW`s) utilizing functions like `argMax()` or `LIMIT 1 BY` to instantly project the absolute latest valid state for any given `experiment_id` and `agent_id`.
* **State Assembly:** These views will logically group the latest `KVMemory`, `StreamMemory`, `SpatialMemory`, and pending `Messager` queues to be efficiently pulled by the `SimulationEngine` during the rehydration phase.
